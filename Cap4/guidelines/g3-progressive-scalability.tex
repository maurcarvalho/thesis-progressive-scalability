\section{G3: Design for Progressive Scalability}
\label{sec:g3-design-progressive-scalability}

G3 focuses on designing modular monoliths so that scalability is achieved progressively rather than through premature distribution. \emph{Progressive scalability} is the capacity of a modular monolith to accommodate increasing load, data volume, and organizational growth through a deliberate sequence of architectural steps, each proportional to the observed need, without requiring a wholesale migration to a distributed architecture.

G3 requires that G1 boundaries are enforced and G2 maintainability discipline is in place. It completes the Architectural Design Dimension (G1--G3): G1 enforces modular boundaries, G2 preserves maintainability through bounded cost of change, and G3 ensures that the resulting structure can accommodate growth without collapsing into either a monolithic bottleneck or a premature microservices decomposition.

\subsection*{Intent and Rationale}

The prevailing narrative in cloud-native literature frames scalability as an inherently distributed concern: when the system must scale, it must be decomposed into independently deployable services~\cite{arya2024beyond, blinowski2022monolithic}. This framing creates a false dichotomy. Teams are implicitly told to choose between a monolith that cannot scale and microservices that can, ignoring the intermediate architectural states that a well-modularized monolith can occupy. In practice, load concentrates in specific modules and specific data domains expand faster than others. A system designed for progressive scalability acknowledges this unevenness and provides mechanisms to address it in a targeted manner.

G3 treats scalability as a \emph{spectrum} rather than a binary switch. The guideline defines a four-level Progressive Scalability Spectrum (Table~\ref{tab:scalability-spectrum}): \emph{Tune} (vertical optimization), \emph{Decouple} (asynchronous boundaries), \emph{Isolate} (data separation), and \emph{Extract} (selective service extraction) as a last resort. Each level is triggered by observable metrics rather than speculative anticipation, and each step is reversible if conditions change.

\subsection*{Objectives}

\emph{Research contributions:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Formalize scalability as a metric-driven spectrum:} Define a progression spectrum (Tune, Decouple, Isolate, Extract) where each transition is governed by quantifiable thresholds, replacing the binary monolith-or-microservices framing with a sequence of proportional, reversible steps.
  \item \emph{Synthesize cross-guideline extraction readiness:} Combine boundary health (G1), maintainability signals (G2), and scalability preparation (G3) into a per-module score that grounds extraction decisions in architectural evidence rather than intuition. No existing work in the SLR corpus provides such a cross-concern composite for modular monoliths.
\end{itemize}

\emph{Implementation objective:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Embed scalability infrastructure from the start:} Design the architecture so that the infrastructure for all spectrum levels (caching, async channels, schema isolation) is present from the initial deployment. Infrastructure abstraction and extraction optionality are addressed in the Key Principles below.
\end{itemize}


\subsection*{Key Principles}

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Scale where it hurts, not where it might:}
  Scaling actions are driven by observed bottlenecks, not speculative anticipation. Module-level metrics provide the evidence base.

  \item \emph{Asynchronous boundaries enable independent scaling:}
  The boundary between two modules becomes a scalability boundary when their throughput requirements diverge. An asynchronous channel at this boundary accommodates load spikes without propagating cascading load to the consumer.

  \item \emph{Infrastructure and data are abstraction-ready from the start:}
  G1 establishes per-module schemas. G3 extends this by requiring that both data access and infrastructure dependencies are mediated through ports and published contracts, so that any spectrum transition is a configuration change rather than a rewrite.

  \item \emph{Every step is reversible by design:}
  Each spectrum-level transition preserves the option to roll back. Infrastructure abstractions and communication channels are structured so that reverting requires configuration changes, not architectural rework.
\end{itemize}

\subsection*{Implementation Mechanisms}

G3 is implemented through three architectural mechanisms, all established at project start:

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Module-scoped resource profiling:} Each module's resource consumption is attributable through instrumentation or naming conventions. Concrete instrumentation is demonstrated in G6 (Observability Patterns); G3 defines the architectural requirement.

  \item \emph{Communication abstraction layer:} Inter-module communication passes through a contract-based abstraction (event bus, command dispatcher) that can be backed by in-process dispatch, an in-memory queue, or a distributed broker such as Apache Kafka without changing the caller or handler.

  \item \emph{Persistence port pattern:} Each module accesses its data through repository interfaces backed by a dedicated database schema declared via \texttt{pgSchema()}. When a module reaches the Extract level, the adapter is re-bound to a dedicated database instance without changing domain logic.

\end{itemize}

\subsection*{Common Failure Modes and Anti-Patterns}

G1 and G2 anti-patterns remain relevant at the G3 level. The five patterns below pass both G1 and G2 gates but compromise the system's ability to scale progressively.

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \textbf{Premature Distribution} ($\varepsilon_m < 1.0$)\\
  A team extracts a module into its own service because ``it handles the most traffic,'' despite low throughput divergence and incomplete schema isolation. Re-embedding the module later requires undoing infrastructure, CI, and data ownership changes~\cite{gravanis2021dont, su2024from}.
  \emph{Approach:} require all five Extraction Readiness components to meet their targets ($\varepsilon_m = 1.0$) before any extraction decision.

  \item \textbf{Uniform Scaling Assumption} ($\Delta\Theta$ not monitored)\\
  All modules are deployed behind identical auto-scaling rules, even though one handles 10$\times$ the traffic of the others. Underloaded modules waste resources while the overloaded one remains constrained.
  \emph{Approach:} monitor Module Throughput Profile ($\Theta_m$) per module and scale only the modules that need it.

  \item \textbf{Shared Database as Implicit Coupling} ($\omega < 1.0$)\\
  One module runs \texttt{SELECT} queries directly against another module's tables. When the owning module refactors its schema, the dependent module's queries break silently, and neither can be extracted independently.
  \emph{Approach:} enforce per-module \texttt{pgSchema()} and expose needed data through domain events.

  \item \textbf{Synchronous Call Chains Under Load} ($\rho_{\mathrm{sync}} > 0.3$)\\
  A workflow calls multiple modules synchronously in sequence: validate stock, then charge payment, then create shipment. A latency spike in any downstream module blocks the entire chain, propagating failures upstream.
  \emph{Approach:} replace synchronous calls with event-driven choreography or, when orchestration is needed, a dedicated saga.

  \item \textbf{Infrastructure Lock-In} ($\alpha < 1.0$)\\
  Domain services call \texttt{redis.get()} and \texttt{kafka.produce()} directly instead of using adapter interfaces. Transitioning from Tune to Decouple requires rewriting business logic to swap the infrastructure provider.
  \emph{Approach:} access all infrastructure through port interfaces; swap implementations via adapter pattern.
\end{itemize}

\subsection*{The Progressive Scalability Gap}

The Progressive Scalability Gap is the distance between architectural correctness and scalability readiness. A module can have perfect boundary scores (G1) and stable maintainability trends (G2) while sharing a database connection pool with three other modules, communicating exclusively through blocking calls, and depending on infrastructure through concrete implementations. When load arrives, scaling such a module requires a coordinated migration rather than a targeted step.

A system closes this gap not by distributing prematurely, but by progressively preparing its modules for independent scaling: isolating data, abstracting infrastructure, and introducing asynchronous boundaries before they are needed. G3's metrics make this preparation visible and measurable.

\noindent
Where G2 metrics are continuous values that reveal trends, G3 metrics split into two categories. Monitoring indicators (Throughput Divergence, Latency Variance) have no pass/fail threshold; they signal when a module should transition to the next spectrum level. Verification metrics (Sync Ratio, Data Ownership, Abstraction Coverage) are hard gates that must be met before extraction is considered. Formal definitions for each metric are provided in Appendix~\ref{app:metrics-g3}.

The Extraction Readiness Score ($\varepsilon_m$) synthesizes G1 boundary health, G2 maintainability, and G3 scalability signals into a per-module readiness score. G2 compliance acts as a binary prerequisite: all six G2 metrics must meet their targets before extraction readiness is assessed.
\[
  \varepsilon_m = 0.25 \cdot b_m + 0.25 \cdot (1 - \rho_{\mathrm{sync}}^{(m)}) + 0.20 \cdot g_m + 0.15 \cdot \omega_m + 0.15 \cdot v_m
\]
where $b_m$ = boundary compliance (G1), $(1 - \rho_{\mathrm{sync}}^{(m)})$ = async readiness, $g_m$ = G2 compliance (1 if all six targets met, 0 otherwise), $\omega_m$ = schema isolation, $v_m$ = event contract versioning.
The score ranges from 0 to 1 and tracks how close a module is to extraction readiness. Extraction requires $\varepsilon_m = 1.0$, meaning all five components meet their targets. Values below 1.0 indicate which dimensions still need preparation. The relative ranking of weights reflects the literature: boundary compliance and async readiness carry the highest weight because they most directly determine whether a module can operate independently. The specific numerical weights are proposed by this work and remain subject to empirical validation through practitioner interviews.


\subsection*{Literature Support Commentary}

Comparative analyses demonstrate that the monolith-versus-microservices trade-offs are context-dependent, yet stop short of proposing what a team should do between these two poles~\cite{jatkiewicz2023differences, berry2024isItWorth}. Industry experience reinforces the ambiguity: documented retreats from microservices~\cite{segment2023, auth02019} and evidence that monoliths remain viable at significant scale~\cite{medium2019} suggest that distribution is not a universal solution~\cite{lima2024accelerating, gravanis2021dont}.

Two proposals come closest to progressive scalability. The ``sliceable monolith''~\cite{montesi2021sliceable} keeps the system unified until a slice needs independent deployment, but focuses on deployment granularity rather than the intermediate steps (async boundaries, data isolation, infrastructure abstraction) that precede extraction. The Strangler Fig pattern~\cite{stranglerPatterns} offers incremental migration but operates at the application boundary rather than addressing internal modular preparation. The evolutionary architecture perspective~\cite{FordParsons2017} provides the philosophical foundation but does not operationalize it for scaling decisions at the module level.

No existing work in the SLR corpus provides a formalized intermediate-state model between monolith and microservices, quantified progression triggers, or a composite extraction readiness metric synthesizing signals across guidelines. G3 addresses these three gaps.

\subsection*{Core Contribution}

G3 contributes to the modular monolith literature in three ways:

\begin{enumerate}[itemsep=8pt,topsep=2pt]
  \item \emph{A formalized scalability spectrum.} The Progressive Scalability Spectrum replaces the binary ``monolith or microservices'' framing with four intermediate states (Tune, Decouple, Isolate, Extract), each with explicit metric triggers and rollback paths.

  \item \emph{Metric-driven progression triggers.} Each transition is governed by quantifiable thresholds that remove subjectivity. The metrics build on G1's boundary health and G2's maintainability signals, creating a composable chain across guidelines.

  \item \emph{Per-module, reversible steps.} Scaling decisions are scoped to individual modules and each step is reversible through adapter abstractions, preserving architectural optionality~\cite{gravanis2021dont, segment2023}.
\end{enumerate}

\subsection*{G3 Applied: Progressive Scalability in the Tiny Store}
\label{sec:g3-applied}

The following sections demonstrate the progressive scalability infrastructure in the Tiny Store reference implementation.\footnote{Full source: \url{https://github.com/maurcarvalho/tiny-store}}

\subsubsection*{Tune: Module-Scoped Caching}

The \texttt{CacheService} enforces module-namespaced keys through a \texttt{buildKey()} method, ensuring cache entries are isolated per bounded context. An \texttt{InMemoryCacheAdapter} serves development; a \texttt{RedisCacheAdapter} is injected for production:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={CacheService with module-namespaced keys (cache.service.ts)},label={lst:g3-cache-service}]
class CacheService {
  private adapter: CacheAdapter;
  private globalPrefix: string;

  private buildKey(module: string, key: string): string {
    return `${this.globalPrefix}:${module}:${key}`;
  }
  // get() and set() delegate to this.adapter via buildKey()
}
\end{lstlisting}

\noindent
A read-through caching decorator applies this pattern declaratively. When Tune-level optimization is needed, the team adds \texttt{@Cacheable('inventory', 60, (sku) => `product:\$\{sku\}`)} to the target method.\footnote{Full decorator: \texttt{libs/shared/infrastructure/src/cache/cache.decorator.ts}}

\subsubsection*{Decouple: Module-Scoped Queues}

The \texttt{QueueService} provides module-scoped queues following the \texttt{module:purpose} naming convention, with the same adapter pattern as the cache layer:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={QueueService with adapter pattern (queue.service.ts)},label={lst:g3-queue-service}]
class QueueService {
  private adapter: QueueAdapter;

  async enqueue<T>(queue: string, data: T,
                   options?: JobOptions): Promise<Job<T>> {
    return this.adapter.enqueue(queue, data, options);
  }

  registerWorker<T>(queue: string,
                    handler: WorkerHandler<T>): void {
    this.adapter.registerWorker(queue, handler);
  }
}
\end{lstlisting}

\noindent
The \texttt{InMemoryQueueAdapter} ships with the initial deployment; a \texttt{BullMQAdapter} backed by Redis is injected when \texttt{REDIS\_URL} is defined.\footnote{Adapters and factory: \texttt{libs/shared/infrastructure/src/queue/}} The composition root selects the adapter based on the environment variable: removing \texttt{REDIS\_URL} reverts the entire queue infrastructure to in-memory dispatch. The same pattern applies to the event bus: at the Tune level, events are dispatched in-process; when a module pair triggers the Decouple threshold, the adapter switches to a Kafka topic using the same event contracts.

\subsubsection*{Isolate: Per-Module PostgreSQL Schemas}

Each module declares its own PostgreSQL schema using Drizzle ORM's \texttt{pgSchema()} API, co-located with the module source:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={Per-module PostgreSQL schema isolation (inventory/db/schema.ts)},label={lst:g3-schema-isolation}]
import { pgSchema, text, integer, timestamp }
  from 'drizzle-orm/pg-core';

const inventorySchema = pgSchema('inventory');

export const productsTable = inventorySchema.table('products', {
  id: text('id').primaryKey(),
  sku: text('sku').notNull(),
  name: text('name').notNull(),
  stockQuantity: integer('stock_quantity').notNull(),
  reservedQuantity: integer('reserved_quantity').notNull(),
  status: text('status').notNull(),
  createdAt: timestamp('created_at').notNull(),
  updatedAt: timestamp('updated_at').notNull(),
});
// orders, payments, shipments follow the same pattern
\end{lstlisting}

\noindent
Because \texttt{pgSchema()} is the single source of truth, no central configuration is required. Drizzle qualifies all queries with the schema prefix (e.g., \texttt{inventory.products}), making cross-schema access impossible through the ORM layer. When Extract-level extraction occurs, the module changes its connection string to a dedicated instance; schema declarations, repositories, and domain logic remain unchanged.

When monitoring signals (connection pool saturation, lock wait times, replication lag) indicate that a module needs a dedicated database instance, the transition is itself progressive: provision the instance and rebind the connection string. The schema, tables, and queries remain identical.

\subsubsection*{Extract: What Extraction Looks Like}

Extract is reached only when Tune, Decouple, and Isolate have been exhausted for a specific module. At this point, the module is already decoupled asynchronously and owns its data exclusively. Extraction is a topology change: the domain logic, repository interfaces, and event handlers remain unchanged. The Tiny Store repository includes a working example (\texttt{docker-compose.l3.yml})\footnote{Full file: \url{https://github.com/maurcarvalho/tiny-store/blob/main/docker-compose.l3.yml}} that deploys Orders as an independent service:

\needspace{4\baselineskip}
\begin{lstlisting}[language=yaml,caption={Extract-level topology (docker-compose.l3.yml, abbreviated)},label={lst:g3-l3-extraction}]
services:
  orders-service:  # own API (port 3001) + own DB + own events
    build: { context: ., dockerfile: apps/orders-service/Dockerfile }
    ports: ['3001:3001']
    environment:
      DATABASE_URL: postgres://orders:orders@orders-db:5432/orders
      REDIS_HOST: redis
    depends_on:
      orders-db: { condition: service_healthy }

  orders-db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: orders

  monolith:  # serves inventory, payments, shipments on port 3000
    environment:
      DATABASE_URL: postgres://tinystore:tinystore@main-db:5432/tinystore
      EXTRACTED_MODULES: orders  # middleware returns 410 Gone
\end{lstlisting}

\noindent
In production, the monolith and extracted service communicate through Kafka topics; event contracts remain identical. Three infrastructure changes occur, none touching domain logic:

\begin{enumerate}[itemsep=4pt,topsep=2pt]
  \item \texttt{DATABASE\_URL} points to a dedicated instance; schema and queries are identical.
  \item Event listeners are scoped to Orders-related events in the service's own entry point.
  \item The service runs in its own container with independent deployment pipeline.
\end{enumerate}

\noindent
The operational concerns of extraction (saga orchestration, event versioning, deployment pipelines) are addressed in G4 and G5. G3 establishes the structural preparation; G4 and G5 address the operational execution.

\subsubsection*{Extraction Readiness Score}

Tiny Store includes an automated extraction readiness calculator that scores each module across five dimensions corresponding to the $\varepsilon_m$ formula:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={Extraction readiness scoring (extraction-readiness.ts)},label={lst:g3-readiness-score}]
const checks: CheckResult[] = [
  checkCrossModuleImports(mod),        // 25 pts (G1)
  checkEventBusUsage(mod),             // 20 pts (async)
  checkAntiCorruptionLayer(mod),       // 15 pts (G2)
  checkSchemaIsolation(),              // 20 pts (data)
  checkVersionedEvents(mod),           // 20 pts (events)
];
\end{lstlisting}

\noindent
In the Tiny Store, the Orders module scores 100/100 ($\varepsilon_m = 1.00$) because all boundaries are enforced, events are versioned, and schemas are isolated. In systems with mixed communication patterns, async readiness should be computed as a continuous ratio rather than a binary check.

\subsubsection*{Exercise 1: Synchronous Cross-Module Call (Sync Ratio $\uparrow$)}
A blocking call is introduced between modules, coupling their availability and degrading async readiness. Modify \texttt{create-shipment/service.ts} to import and call \texttt{GetPaymentHandler} from the payments module:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={Violation: synchronous cross-module import},label={lst:g3-ex1-violation}]
/**
 * (*@\color{red}{$\times$}@*) VIOLATION: synchronous cross-module import.
 */
import { GetPaymentHandler } from '@tiny-store/modules-payments';
const payment = await this.getPaymentHandler.handle(dto.orderId);
\end{lstlisting}

\noindent
G1/G2 pass: the import uses the public entrypoint. G3 fails: sync ratio rises.\\
\textbf{Fix:} enrich the \texttt{OrderPaid} event payload with payment status.\\
Reference: \texttt{exercises/g3/ex1-sync-payment-check.ts}

\subsubsection*{Exercise 2: Shared Table Access (Data Ownership $\downarrow$)}
A raw SQL query reads directly from another module's table, breaking data isolation without triggering any import violation. In the orders module, add:

\needspace{4\baselineskip}
\begin{lstlisting}[language=TypeScript,caption={Violation: cross-module table access},label={lst:g3-ex2-violation}]
/**
 * (*@\color{red}{$\times$}@*) VIOLATION: orders reads inventory's table directly.
 */
const productRows = await this.db.execute(
  sql`SELECT stock_quantity FROM inventory.products
      WHERE sku = ${item.sku}`
);
\end{lstlisting}

\noindent
G1/G2 pass: no module import, only raw SQL. G3 fails: data ownership drops below 1.0.\\
\textbf{Fix:} expose stock availability through an \texttt{InventoryUpdated} event.\\
Reference: \texttt{exercises/g3/ex2-shared-inventory-view.ts}

\subsection*{Conclusion}

G3 demonstrated that scalability in a modular monolith is a spectrum traversed through proportional steps: vertical optimization before async decoupling, async decoupling before data isolation, data isolation before extraction. The Tiny Store reference implementation shows that infrastructure for all four levels can be established from the initial deployment, making scalability a structural property rather than a future migration.

With boundaries enforced (G1), maintainability preserved (G2), and scalability infrastructure prepared (G3), the architecture is structurally ready for growth. G4 addresses the next concern: when a module's extraction readiness score warrants the Extract level, how to prepare it for independent deployment through event-driven contracts, saga orchestration, and controlled topology changes.
