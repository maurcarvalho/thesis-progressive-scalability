\section{G4: Promote Migration Readiness}
\label{sec:g4-promote-migration-readiness}

G4 embeds migration readiness as a proactive design property so that extracting a module from the monolith becomes a controlled, low-risk operation. Where G1--G3 address boundaries, maintainability, and scalability within the monolith, G4 ensures that the transition to independent deployment, when justified by G3's Extract level, does not require a rewrite.

\subsection*{Intent and Rationale}

Migration from a monolith to microservices is one of the most expensive architectural transitions a team can undertake. Studies consistently report that migration efforts are dominated not by the extraction itself, but by the discovery and resolution of hidden coupling: shared database tables, implicit co-location assumptions, synchronous call chains that mask network-boundary failures, and domain logic scattered across modules~\cite{fritzsch2019, abgaz2023decomposition, wolfart2021modernizing}.

The root cause is that most monoliths are not designed with extraction in mind. Dependencies accumulate implicitly, persistence is shared by convention, and inter-module communication relies on in-process guarantees (transactions, shared memory, synchronous calls) that do not survive a network boundary. When migration pressure arrives, teams discover that the actual cost of extraction is proportional to the amount of implicit coupling that must be made explicit.

G4 inverts this dynamic. Instead of treating migration as a future problem, G4 embeds readiness into the module's design from the outset. The cost is incremental: designing internal APIs, introducing Anti-Corruption Layers, and avoiding shared mutable state improve the system independent of whether extraction ever occurs. The benefit is optionality: when extraction is justified, the module is already prepared.

\subsection*{Objectives}

\emph{Research contributions:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Formalize migration readiness as a continuous property:} Define extraction preparation as a measurable, incremental investment rather than a migration-phase activity.
  \item \emph{Bridge the readiness gap:} Identify the structural conditions (Anti-Corruption Layers, saga completeness, API versioning) that separate ``architecturally correct'' modules from ``extraction-ready'' modules, extending G3's scalability preparation into operational readiness.
  \item \emph{Treat extraction as a configuration change:} Demonstrate that a properly prepared module can transition from monolith to independent service by changing infrastructure wiring, not domain logic.
\end{itemize}

\emph{Implementation objectives:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Version all cross-module contracts:} Module public surfaces carry version metadata, enabling backward-compatible evolution after extraction.
  \item \emph{Mediate integration through Anti-Corruption Layers:} Each module translates inbound and outbound data through an explicit mapping layer so that internal model changes do not propagate across boundaries.
  \item \emph{Replace cross-module transactions with sagas:} Design cross-module workflows as compensable sequences that function correctly across process boundaries.
\end{itemize}

\subsection*{Key Principles}

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Anti-Corruption Layers prevent model leakage:} Each module has its own domain model and vocabulary. When module $A$ consumes data from module $B$, it should not depend on $B$'s internal representation. An Anti-Corruption Layer translates between domain models, decoupling their evolution so that extraction requires only a transport change, not an interface redesign~\cite{evans2003ddd}.

  \item \emph{Eventual consistency is the default for cross-module workflows:} Monoliths often rely on database transactions to maintain consistency across modules. This works in-process but fails across network boundaries. Saga patterns replace atomic transactions with compensable sequences: each module performs its local operation and publishes an event; failures trigger compensating actions. Introducing sagas before extraction forces the team to confront distributed failure modes while the system is still co-located and easier to debug~\cite{richardson2018microservices}.

  \item \emph{Infrastructure wiring is the extraction knob:} When a module is ready for extraction, the change should be localized to the composition root: swap the in-process event bus for a distributed broker, replace the shared database connection with a dedicated one, and route API calls through a network client. If extraction requires changes to domain logic, the module is not yet migration-ready~\cite{ghemawat2023towards}.

  \item \emph{Internal APIs deserve external-grade rigor:} In-process interfaces invite informality because breaking changes are discovered immediately. This convenience creates migration debt. When internal APIs are designed with versioning and backward compatibility, extraction requires only a transport layer change~\cite{parnas1972informationhiding}.
\end{itemize}

\subsection*{Implementation Mechanisms}

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Anti-Corruption Layer gateways:} Each cross-module integration point is mediated by a gateway interface with an in-process adapter. After extraction, only the adapter implementation changes (in-process call to HTTP/gRPC client); the gateway contract and all consuming code remain unchanged.

  \item \emph{Saga orchestration inside the monolith:} Cross-module workflows are orchestrated through a durable execution engine (e.g., Temporal) that provides retry policies, timeout handling, and compensating actions. The workflow runs inside the monolith from day one; after extraction, the same workflow code executes unchanged with activities routed over the network.

  \item \emph{Event streaming with durable delivery:} Domain events are published to durable, partitioned topics (e.g., Kafka) with per-module topic naming. Consumer groups support horizontal scaling of listeners. This infrastructure operates inside the monolith and survives extraction without reconfiguration.

  \item \emph{Versioned event contracts:} Each event type carries an explicit schema version. A factory function enforces the current version; consumers include version-aware deserialization so that schema evolution does not break downstream modules.
\end{itemize}

\subsection*{Common Failure Modes and Anti-Patterns}

G1--G3 anti-patterns remain relevant at the G4 level. The five patterns below pass all prior gates but compromise the system's ability to extract modules as independent services.

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \textbf{Deferred Readiness} (extraction cost rises over time)\\
  Postponing migration preparation until extraction is imminent. At that point, accumulated coupling (shared tables, implicit transactions, unversioned APIs) makes extraction a multi-month project instead of a configuration change.
  \emph{Approach:} treat readiness as a continuous investment; apply G4 steps incrementally from the first sprint.

  \item \textbf{Shared Database as Hidden Integration} (Data Ownership below 100\%)\\
  Two modules that appear decoupled at the code level share database tables, coupling them at the persistence level. This is the most common and most expensive migration blocker~\cite{fritzsch2019}.
  \emph{Approach:} enforce per-module \texttt{pgSchema()} and expose needed data through domain events.

  \item \textbf{Cross-Module Transactions Masking Failure Modes} (Saga Completeness below 100\%)\\
  Relying on database transactions across modules hides the failure modes that will surface after extraction. When inventory reservation and order creation share a transaction, partial failure is impossible; after extraction, partial failure is the default~\cite{richardson2018microservices}.
  \emph{Approach:} introduce saga orchestration inside the monolith before extraction.

  \item \textbf{Payload Coupling Without Anti-Corruption Layers} (Anti-Corruption Layer Coverage below 100\%)\\
  Downstream modules consume event payloads directly without translation. Any change to the upstream module's event schema breaks all consumers simultaneously, creating a coordination bottleneck incompatible with independent deployment~\cite{evans2003ddd}.
  \emph{Approach:} place an Anti-Corruption Layer at each integration point to translate between domain models.

  \item \textbf{Premature Extraction Without Readiness} ($\varepsilon_m = 0$)\\
  Extracting a module with shared state, no Anti-Corruption Layers, and no saga creates a distributed monolith: the operational complexity of microservices with the coupling characteristics of a monolith~\cite{gravanis2021dont}.
  \emph{Approach:} require $\varepsilon_m = 1$ and all G4 preparation steps complete before initiating extraction.
\end{itemize}

\subsection*{The Migration Readiness Gap}
\label{sec:g4-readiness-gap}

The Migration Readiness Gap is the distance between scalability readiness (G3) and operational readiness for extraction. A module can achieve $\varepsilon_m = 1$ on G3's structural metrics while lacking the operational infrastructure that makes extraction survivable: no Anti-Corruption Layers to absorb schema changes, no saga orchestration to handle distributed failures, and no versioned contracts to support independent deployment.

G3 cannot detect this because it validates structural preparation (async boundaries, schema isolation, infrastructure abstraction), not operational preparation (failure handling, contract evolution, cross-service coordination). The Migration Readiness Gap widens when teams treat G3 compliance as sufficient for extraction, skipping the Anti-Corruption Layers and saga patterns that distinguish a configuration change from a rewrite.

G4 closes this gap by making operational readiness visible and measurable before extraction is attempted.

\subsection*{Core Contribution}

G4 contributes to the modular monolith literature in three ways:

\begin{enumerate}[itemsep=8pt,topsep=2pt]
  \item \emph{Migration readiness as a continuous design property.} Existing literature treats migration as a phase-specific activity~\cite{wolfart2021modernizing, abgaz2023decomposition}. G4 reframes it as an incremental investment that improves the system independent of whether extraction occurs, building on the proactive readiness concept absent from current decomposition research.

  \item \emph{The Migration Readiness Gap as a formal concept.} G4 names the phenomenon where a module passes all structural gates (G1--G3) but lacks operational infrastructure for safe extraction (Section~\ref{sec:g4-readiness-gap}), analogous to G2's Incremental Maintainability Degradation and G3's Progressive Scalability Gap.

  \item \emph{Saga-first orchestration inside the monolith.} The saga pattern is well-established for distributed systems~\cite{richardson2018microservices} but rarely discussed as a monolith-internal pattern. G4 argues that sagas should be introduced before extraction, while the system is co-located and easier to debug, rather than after extraction when distributed failure modes make design significantly harder.
\end{enumerate}

\subsection*{Literature Support Commentary}

Migration from monoliths to microservices is extensively studied. Reviews of decomposition techniques show that most approaches focus on identifying service candidates rather than on preparing the monolith for extraction~\cite{abgaz2023decomposition}. Modernization roadmaps acknowledge that proactive readiness remains underexplored~\cite{wolfart2021modernizing}, and surveys confirm that hidden coupling and shared state are the dominant cost drivers~\cite{fritzsch2019, salii2023migrating}. Incremental transition strategies emphasize planning the migration path from the outset~\cite{bozan2020transition}.

The Anti-Corruption Layer concept originates in Domain-Driven Design~\cite{evans2003ddd} as a boundary mechanism between bounded contexts. Its application to modular monoliths as a proactive migration preparation technique, rather than a reactive integration fix, is novel in this context. The saga pattern~\cite{richardson2018microservices} is similarly recontextualized: G4 introduces it inside the monolith before extraction, leveraging durable execution engines that persist workflow state and provide the same guarantees whether activities are in-process or networked.

Service Weaver~\cite{ghemawat2023towards} treats distribution as a deployment concern rather than a development concern. G4 adopts this philosophy: modules are designed with clean boundaries (G1--G3), but their deployment topology is determined by configuration. When extraction is warranted, infrastructure wiring changes; domain logic does not.

\section{G4 Applied: Migration Readiness in the Tiny Store}
\label{sec:g4-applied}

G4 is demonstrated through the Orders module, the highest-traffic path and the most probable extraction candidate.\footnote{Full source: \url{https://github.com/maurcarvalho/tiny-store}} The case study examines what Orders already does well and the preparation steps needed for production-grade extraction readiness.

\subsection*{Current State}

The Orders module already satisfies several migration readiness properties by construction: an explicit public surface (\texttt{@tiny-store/modules-orders} re-exports only handlers and event contracts), event-driven collaboration through domain events wired in the composition root, and no direct imports between Orders and other modules. At the code level, extracting Orders would not require rewriting cross-module interactions.

\subsection*{Migration Readiness Gaps}

Despite strong boundary enforcement, the baseline state reflects a common pattern: boundaries are clean at the code level, but the infrastructure layer still assumes co-location. These gaps appear in virtually every modular monolith that has not been deliberately prepared for extraction:

\begin{enumerate}[itemsep=8pt,topsep=2pt]
  \item \emph{No Anti-Corruption Layers:} Downstream modules consume event payloads directly. Schema changes in Orders break all consumers simultaneously.
  \item \emph{No saga orchestration:} The event choreography (OrderPlaced $\to$ InventoryReserved $\to$ PaymentProcessed $\to$ ShipmentCreated) distributes saga logic implicitly across listeners. Failure visibility is poor, retry policies are ad hoc, and compensating actions are scattered.
  \item \emph{No API versioning:} Event contracts and handler interfaces carry no version metadata, preventing independent evolution after extraction.
\end{enumerate}

\subsection*{Tutorial: Step-by-Step Application}

The following steps prepare the Orders module for extraction without extracting it. Each step introduces production-grade infrastructure that functions identically before and after extraction.

\subsubsection*{Step 1: How do we decouple domain models across modules?}

Introduce Anti-Corruption Layer gateways that translate between domain models. After extraction, only the adapter implementation changes:

\begin{lstlisting}[language=TypeScript,caption={Anti-Corruption Layer gateway for inventory integration},label={lst:g4-acl-inventory}]
export interface InventoryGateway {
  reserveItems(orderId: string, items: OrderItem[]): Promise<Result>;
  releaseItems(orderId: string): Promise<void>;
}
// In-process adapter today; HTTP/gRPC adapter after extraction.
// Gateway contract and consuming code remain unchanged.
\end{lstlisting}

\subsubsection*{Step 2: How do we handle cross-module failures explicitly?}

Replace implicit event choreography with an explicit saga workflow. The workflow makes the full compensation path visible in a single file:

\begin{lstlisting}[language=TypeScript,caption={Order fulfillment saga with compensating actions},label={lst:g4-temporal-workflow}]
export async function orderFulfillmentWorkflow(input: OrderInput) {
  const reservation = await reserveInventory(input);
  if (!reservation.success) return { success: false };
  try {
    const payment = await processPayment(input);
    if (!payment.success) {
      await releaseInventory(input); // compensate
      return { success: false };
    }
    const shipment = await createShipment(input);
    return { success: true, trackingNumber: shipment.trackingNumber };
  } catch (err) {
    await refundPayment(input);      // compensate
    await releaseInventory(input);   // compensate
    throw err;
  }
}
\end{lstlisting}

\noindent
Activities call module handlers through Anti-Corruption Layer gateways. After extraction, the same workflow runs unchanged; only the activity implementations switch from in-process calls to network calls.\footnote{Full workflow and activities: \texttt{libs/modules/orders/src/workflows/}}

\subsubsection*{Step 3: How do we enable independent contract evolution?}

Add version metadata to event contracts so that consumers can handle schema evolution:

\begin{lstlisting}[language=TypeScript,caption={Versioned event contract with factory},label={lst:g4-versioned-event}]
export interface OrderPlacedPayload {
  orderId: string;
  items: Array<{ sku: string; quantity: number; unitPrice: number }>;
  total: number;
  version: 1;  // explicit schema version
}

export function createOrderPlacedEvent(orderId: string,
  payload: Omit<OrderPlacedPayload, 'version'>): OrderPlacedEvent {
  return { eventType: 'OrderPlaced', aggregateId: orderId,
    payload: { ...payload, version: 1 } };
}
\end{lstlisting}

\subsection*{Exercise Walkthrough: Controlled Violations and Signals}

Each exercise introduces a change that passes G1--G3 gates but degrades a specific G4 metric.

\subsubsection*{Exercise 1: Direct Payload Consumption (Anti-Corruption Layer Coverage $\downarrow$)}

A downstream module consumes an event payload without translation:

\begin{lstlisting}[language=TypeScript,caption={Violation: direct payload coupling without Anti-Corruption Layer},label={lst:g4-ex1-violation}]
// Shipments directly destructures Orders' payload format
eventBus.subscribe('OrderPaid', async ({ payload }) => {
  // If Orders renames 'shippingAddress' to 'deliveryAddress',
  // this handler breaks silently
  await createShipment(payload.orderId, payload.shippingAddress);
});
\end{lstlisting}

\noindent
G1--G3 pass: the subscription uses the public event bus. G4 fails: Anti-Corruption Layer Coverage drops.\\
\textbf{Fix:} introduce a gateway that translates the payload into Shipments' own domain model.

\subsubsection*{Exercise 2: Implicit Compensation (Saga Completeness $\downarrow$)}

A cross-module workflow handles failures with ad hoc try/catch instead of explicit compensating actions:

\begin{lstlisting}[language=TypeScript,caption={Violation: ad hoc error handling instead of saga compensation},label={lst:g4-ex2-violation}]
eventBus.subscribe('PaymentFailed', async ({ payload }) => {
  try {
    await cancelOrder(payload.orderId);
    // Missing: releaseInventory() compensation
  } catch (err) { console.error('cleanup failed', err); }
});
\end{lstlisting}

\noindent
G1--G3 pass: no boundary or scalability violation. G4 fails: Saga Completeness drops because the compensation path is incomplete.\\
\textbf{Fix:} model the workflow as an explicit saga with all compensating actions defined.

\subsection*{Conclusion}

G4 demonstrated that migration readiness is a design property, not a migration-phase activity. The Orders case study showed that Anti-Corruption Layers, saga orchestration, and versioned contracts can be introduced inside the monolith, producing a system where extraction requires only infrastructure wiring changes.

With boundaries enforced (G1), maintainability preserved (G2), scalability infrastructure prepared (G3), and migration readiness embedded (G4), the architecture is structurally and operationally ready for extraction. G5 addresses the next concern: how the deployment pipeline adapts to support both monolith and extracted-service topologies.
