\section{G2: Embed Maintainability}
\label{sec:g2-embed-maintainability}

G2 embeds maintainability as an architectural property by treating the cost of change as a design constraint. While G1 enforces explicit modular boundaries, G2 ensures those boundaries remain effective over time through stable contracts and continuous detection of architectural drift~\cite{gravanis2021dont,blinowski2022monolithic}.

\subsection*{Intent and Rationale}
The primary driver of maintainability degradation is not system size but the accumulation of hidden coupling, ambiguous dependency direction, and architectural drift~\cite{gravanis2021dont,blinowski2022monolithic}. G2 constrains how modules interact and how dependencies are introduced, prioritizing change locality and controlled dependency growth over short-term reuse so that the effort to evolve the system scales sublinearly with its size~\cite{arya2024beyond,berry2024isItWorth}.

\subsection*{Objectives}

\emph{Research contributions:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Frame maintainability as bounded cost of change:} Limit change propagation so that most modifications remain confined to a single bounded context.
  \item \emph{Quantify boundary sustainability:} Establish metrics that distinguish point-in-time correctness (G1) from health over time, detecting drift before it becomes irreversible.
  \item \emph{Formalize the incremental maintainability degradation:} Demonstrate that a system can pass all G1 gates while accumulating maintainability debt through structurally valid patterns.
\end{itemize}

\emph{Implementation objectives:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Dependencies flow toward stability:} Dependencies point from volatile modules (those that change frequently) toward stable ones (those with fewer dependents and slower-changing contracts), not the reverse.
  \item \emph{Stable contracts under evolution:} Track whether public exports are retained across releases so that contract churn does not erode refactoring freedom.
  \item \emph{Trend-aware drift detection:} Extend G1's point-in-time checks with time-series tracking so that gradual degradation is caught before it becomes irreversible.
\end{itemize}

\subsection*{Key Principles}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Reuse through contract, not exposure:} G1 enforces that internals are hidden; G2 adds that cross-module reuse of even public code is a maintainability risk unless mediated through a stable, versioned contract~\cite{parnas1972informationhiding}.
  \item \emph{Dependencies flow toward stability:} Dependencies point from volatile modules toward stable ones; a rarely changing module must not depend on a frequently changing one~\cite{martin2012clean}.
  \item \emph{Change locality within bounded contexts:} Each bounded context owns its model and language; cross-context interaction occurs through explicit contracts, not shared internals~\cite{evans2003ddd}. Most changes should be implementable within a single module.
  \item \emph{Coupling is a spectrum, not a binary:} Data coupling through published events is preferable to content coupling through shared internals~\cite{yourdon1979structured}. G2 metrics quantify where each module sits on this spectrum, making drift visible before it becomes irreversible.
\end{itemize}

\subsection*{Implementation Mechanisms}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Event-carried state transfer:} When a consumer needs data from another module, the domain event payload carries that data rather than the consumer issuing a cross-module query. This preserves change locality and prevents more modules from depending on the provider~\cite{richardson2018microservices}.
  \item \emph{Deliberate contract evolution:} A module's public surface evolves intentionally, not by accumulation. The more modules depend on a given contract, the more conservatively it changes. New exports require justification that they serve cross-module consumers; removals go through a deprecation period so dependents can migrate~\cite{FordParsons2017}.
  \item \emph{Feature scoping within bounded contexts:} New features are designed to be implementable within a single module, keeping new functionality internal rather than forcing new exports across multiple surfaces. When a feature inherently crosses contexts, coordination happens through self-describing domain events, not shared types or transitive handler calls~\cite{evans2003ddd}.
\end{itemize}

\subsection*{Common Failure Modes and Anti-Patterns}

G1 anti-patterns (convenience imports, implicit wiring, circular dependencies) remain relevant at the G2 level. However, G2 introduces a subtler class of failure: patterns that respect every boundary rule yet gradually erode the system's ability to change. These degradations are invisible to point-in-time checks because they accumulate across commits, not within a single snapshot. The three patterns below pass all G1 gates but erode maintainability over time:

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Overloaded Module Exports (Contract Stability drops, Boundary Ratio drops):}
  A module's public entrypoint grows from 7 to 15 exports across three sprints. Each new export is a downstream contractual obligation: once another module depends on it, the export cannot be renamed or removed without coordinated changes~\cite{parnas1972informationhiding}.
  \emph{Approach:} audit each export for cross-module consumers; internalize exports consumed only within the module and expose composite operations instead of granular internals.

  \item \emph{Exposing Internal Types for Cross-Module Convenience (Dependency Attraction rises):}
  A module re-exports an internal type (e.g., an enum or value object) so that another module can use it directly. The import goes through the public entrypoint, so G1 passes. But the dependency graph gains a new module-to-module edge that did not exist at baseline, coupling the consumer to the provider's domain model~\cite{evans2003ddd}.
  \emph{Approach:} carry the needed data in the domain event payload so consumers never import the provider's types.
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Fix: event payload replaces cross-module type import},label={lst:g2-ap-internal-fix}]
// Instead of: import { PaymentStatus } from '@tiny-store/modules-payments';
// The OrderPaid event carries the status the consumer needs:
eventBus.subscribe('OrderPaid', async ({ payload }) => {
  if (payload.verified) await createShipment(payload.orderId);
});
\end{lstlisting}

  \item \emph{Feature-Centric Coupling Across Modules (Change Coupling Index rises):}
  Adding a cross-cutting feature (e.g., ``gift packaging'') requires simultaneous changes to ordering (option flag), billing (fee calculation), and fulfillment (packaging instructions). The feature, not the module, becomes the unit of change, diluting ownership and increasing coordination cost~\cite{FordParsons2017}.
  \emph{Approach:} assign feature ownership to one module; other modules react to domain events and interpret them through their own logic.
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Fix: one module owns the decision; others react},label={lst:g2-ap-feature-fix}]
// Orders owns the gift-wrap decision
orderCreated.emit({ ...order, giftWrap: true });
// Billing reacts independently — no shared types
onOrderCreated(e) { if (e.giftWrap) this.addFee(e.orderId, 'GIFT_WRAP', 4.99); }
\end{lstlisting}
\end{itemize}

\subsubsection*{The Incremental Maintainability Degradation}

\noindent
A system can pass every G1 gate while steadily losing its ability to change. A module whose public surface grows unchecked maintains perfect boundary scores at every checkpoint, yet each new export becomes a contractual obligation that constrains future refactoring.

The pattern is simple. A developer adds an export to solve today's integration need, and the decision is correct in isolation. But adding an export is easy. Removing it requires coordinating every consumer that now depends on it. Over time, coupling accumulates in one direction because there is no natural pressure to reduce it.

Lehman's laws of software evolution observe that actively used programs inevitably grow in complexity unless work is specifically directed at reducing it~\cite{lehman1980programs}. The Incremental Maintainability Degradation is this law manifesting not in the code within modules, but in the contractual surface between them.

G1 cannot detect this because it validates structure, not trajectory. A module with 10 valid exports and one with 50 are equally correct to G1. G2 closes this gap by treating trends as first-class signals, tracking whether the architecture is moving toward or away from sustainability before increasing maintainability costs compromise the ability to achieve progressive scalability.

\subsection*{Metrics and Verification}

G2 inherits all G1 boundary gates and tracks them \emph{over time}. Where G1 metrics are binary (pass or fail at a single checkpoint), G2 metrics are continuous values that reveal both degree and direction, making sustained drift visible before it becomes irreversible.

\subsection*{Core Contribution}

G2 contributes to the modular monolith literature in two ways:

\begin{enumerate}[itemsep=8pt,topsep=2pt]
  \item \emph{The Incremental Maintainability Degradation as a formal concept.} The phenomenon of boundaries eroding over time is well known informally. G2 frames it as a distinct architectural concern, grounded in Lehman's laws of software evolution~\cite{lehman1980programs}, and positions it as the gap between boundary correctness (G1) and boundary sustainability.

  \item \emph{Systematic application of the coupling spectrum to modular monoliths.} Yourdon and Constantine's coupling types~\cite{yourdon1979structured} were defined for modules in general. G2 applies them to bounded contexts where no deployment boundary enforces separation, and provides five metrics that quantify where each module sits on the spectrum, making drift visible and measurable.
\end{enumerate}

\subsection*{Literature Support Commentary}
The microservices literature identifies several maintainability benefits that stem directly from deployment isolation: independent deployability forces explicit contracts, service boundaries prevent accidental coupling, and network latency makes cross-service calls visible and costly enough to discourage them~\cite{fritzsch2019,deLauretis2019from}. These benefits are real, but they come at a significant operational cost: distributed tracing, eventual consistency, contract versioning across network boundaries, and the coordination overhead of managing dozens or hundreds of independently deployed units~\cite{arya2024beyond,berry2024isItWorth}.

G2 argues that most of these maintainability benefits do not depend on deployment separation. They depend on architectural discipline. A module can expose an explicit contract without a network boundary, as long as all cross-module interaction flows through declared public surfaces. A module can evolve independently without independent deployment, as long as changes to its internals do not force changes elsewhere. And coupling can become visible without service failures, as long as metrics track dependency direction, co-change frequency, and API surface growth over time.

Several studies support this position. Modular monoliths can achieve maintainability comparable to microservices when boundary discipline is sustained~\cite{gravanis2021dont,blinowski2022monolithic}. The critical factor is not the deployment model but the consistency of modular enforcement~\cite{wolfart2021modernizing}. Premature migration to microservices often increases maintenance cost without proportional benefit, suggesting that the maintainability gains attributed to microservices may be achievable through less disruptive means~\cite{berry2024isItWorth}.

The challenge, however, is that a monolith provides no natural enforcement mechanism. In a microservices architecture, a broken contract produces a runtime failure. In a monolith, a broken contract produces a successful compilation. Architectural fitness functions have been proposed as a mechanism for continuous validation~\cite{FordParsons2017}, and this concept has been extended into executable checks~\cite{thoughtworks2017fitnessfunction}. G2 builds on both by defining what those fitness functions should measure in a modular monolith: the five metrics above are designed to replicate, through automated measurement, the maintainability feedback that microservices get for free through deployment isolation.

The result is an architecture that captures the maintainability benefits of microservices (explicit contracts, controlled coupling, independent evolvability) without incurring the operational costs of distributed deployment, preserving the option to extract individual modules when, and only when, the evidence justifies it.

\subsection*{G2 Applied: Maintainability in the Tiny Store}
\label{sec:g2-applied}

G2 is demonstrated in the Tiny Store reference implementation.\footnote{Full source: \url{https://github.com/maurcarvalho/tiny-store}} Where G1 focused on the Orders--Inventory boundary, G2 shifts to Payments and Shipments, whose evolution patterns reveal maintainability risks invisible to boundary checks alone.

\subsection*{Tutorial: Step-by-Step Application}

The following steps demonstrate how to measure each G2 metric against the Tiny Store codebase. Starting from the dependency graph and working through API surface, API Boundary Ratio, and Change Coupling Index, each step produces a baseline value that can be tracked over time to detect the Incremental Maintainability Degradation described above.

\subsubsection*{Step 1: Do dependencies flow in the right direction?}

Extract the dependency graph (\texttt{npx nx graph --file=dep-graph.json}). Every bounded-context module depends only on shared libraries; no module-to-module edge exists:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=bash,caption={Expected dependency direction (baseline)},label={lst:g2-dep-baseline}]
  modules-orders    -> shared-domain, shared-infrastructure
  modules-inventory -> shared-domain, shared-infrastructure
  modules-payments  -> shared-domain, shared-infrastructure
  modules-shipments -> shared-domain, shared-infrastructure
\end{lstlisting}

\noindent
If a module-to-module edge appears, coupling has migrated into module internals.

\subsubsection*{Step 2: How large is each module's public surface?}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=bash,caption={Count exports per module},label={lst:g2-api-surface}]
for mod in orders inventory payments shipments; do
  echo "$mod: $(grep -c '^export' libs/modules/$mod/src/index.ts) exports"
done
# orders: 20, inventory: 17, payments: 8, shipments: 9
\end{lstlisting}

These numbers form the $t_0$ snapshot for Contract Stability tracking.

\subsubsection*{Step 3: Are all imports going through the public API?}
All imports in the composition root (\texttt{register-listeners.ts}) use the public path \texttt{@tiny-store/modules-*}, so the API Boundary Ratio is 1.0. Any internal path import would lower this ratio.

\subsubsection*{Step 4: Are changes spreading across module boundaries?}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=bash,caption={Detect co-changing modules in recent commits},label={lst:g2-cci}]
git log --oneline -50 --name-only | \
  awk '/^[a-f0-9]/{c=$1; next}
       /libs\/modules\//{split($0,a,"/"); m[c][a[3]]}
       END{for(c in m) if(length(m[c])>1) print c": "length(m[c])" modules"}'
\end{lstlisting}

In the baseline, only infrastructure commits touch multiple modules; no feature commit crosses module boundaries (Change Coupling Index = 0.0 for feature work).

\subsection*{Exercise Walkthrough: Controlled Maintainability Degradation}
Each exercise introduces a change that passes all G1 boundary tests but degrades a specific G2 metric. Exercises use Payments and Shipments exclusively, with no overlap with G1's Orders--Inventory examples.

\subsubsection*{Exercise 1: Convenience Shortcut That Passes G1 (API Boundary Ratio $\downarrow$)}
A developer re-exports an internal type for cross-module convenience, creating a hidden dependency edge. In \texttt{libs/modules/payments/src/index.ts}, add:
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Step 1: Payments exports an internal enum},label={lst:g2-ex1-step1}]
// "Temporary" export added for cross-module convenience
export * from './domain/enums/payment-status.enum';
\end{lstlisting}

\noindent
Then consume it in \texttt{libs/modules/shipments/src/features/create-shipment/service.ts}:
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Step 2: Shipments depends on Payments' internal type},label={lst:g2-ex1-step2}]
import { PaymentStatus } from '@tiny-store/modules-payments';

if (paymentStatus !== PaymentStatus.SUCCEEDED) {
  throw new Error('Cannot ship unpaid order');
}
\end{lstlisting}

\noindent
Run \texttt{npm run test:boundary}: G1 passes (public entrypoint). But the dependency graph gains a new module-to-module edge (\texttt{shipments $\to$ payments}). Shipments can no longer evolve independently of Payments' domain model.\\
\emph{Resolution:} Remove the enum export; enrich the \texttt{OrderPaid} event payload with payment status instead.

\subsubsection*{Exercise 2: Transitive Orchestration (Forbidden Dependencies $\uparrow$, blast radius)}
Cross-module orchestration is added to the composition root, expanding the blast radius of changes. Modify the \texttt{OrderPaid} subscription in \texttt{register-listeners.ts} to query Payments before creating a shipment:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Violation: three-module orchestration in one handler},label={lst:g2-ex2-violation}]
eventBus.subscribe('OrderPaid', async (event) => {
  const { orderId } = event.payload;
  const payment = await getPaymentHandler.handle(orderId);  // Payments
  if (payment.status === 'REFUNDED') return;
  const order = await getOrderHandler.handle(orderId);      // Orders
  await createShipmentHandler.handle({                      // Shipments
    orderId, shippingAddress: order.shippingAddress });
});
\end{lstlisting}

\noindent
G1 passes, but the handler now orchestrates three modules in sequence. A change to any handler's return type expands the blast radius across Payments, Orders, and Shipments.\\
\emph{Resolution:} Enrich the \texttt{OrderPaid} event payload with all data Shipments needs. If orchestration is necessary, extract it into a dedicated saga.

\subsubsection*{Exercise 3: Public Surface Bloat (Contract Stability $\downarrow$)}
Five valid exports are added in a single sprint, inflating the public surface without violating any boundary rule. In \texttt{libs/modules/payments/src/index.ts}, add:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Surface bloat: valid but excessive exports},label={lst:g2-ex3-violation}]
// --- NEW: 5 additional query handlers in one sprint ---
export * from './features/get-payments-by-order/handler';
export * from './features/get-payments-by-status/handler';
export * from './features/get-payments-by-date/handler';
export * from './features/refund-payment/handler';
export * from './features/retry-payment/handler';
\end{lstlisting}

\noindent
G1 passes (Encapsulation Leakage = 0, all exports are handlers). But Contract Stability drops from 1.0 to 0.62: only 8 of the 13 exports existed in the previous period. Each new export is a downstream obligation that constrains future refactoring.\\
\emph{Resolution:} Remove exports consumed only within the module. Flag Contract Stability drops in CI.

\subsubsection*{Exercise Summary}
All three exercises pass G1 boundary gates:
\begin{itemize}[itemsep=2pt,topsep=2pt]
  \item \textbf{Ex.\,1:} Payments exports enum, Shipments consumes it → new dep edge, API Boundary Ratio drops.
  \item \textbf{Ex.\,2:} Composition root orchestrates 3 modules → blast radius triples.
  \item \textbf{Ex.\,3:} Payments exports 5 valid handlers → Contract Stability drops (1.0 to 0.62).
\end{itemize}

\subsection*{Conclusion}

G1 ensures boundaries are \emph{correct} at any point in time; G2 ensures they remain \emph{sustainable in cost of change} over time. The exercises confirmed that each failure mode produces a measurable signal while passing all G1 gates, validating the complementarity of the two guidelines.

With boundaries enforced (G1) and maintainability preserved (G2), the architecture retains the option to evolve incrementally. G3 addresses the next concern: which scaling steps are proportional to which bottlenecks, and in what order.
