\section{G1: Enforce Modular Boundaries}
\label{sec:g1-enforce-modular-boundaries}

G1 enforces clear modular boundaries to prevent unintended coupling, preserve encapsulation, and ensure that dependencies between modules remain explicit and verifiable through build- and test-time checks.

\subsection*{Intent and Rationale}
Modularity in a monolith should be treated as an enforceable architectural property rather than an assumed outcome of refactoring. Without enforcement, boundaries degrade through convenience-driven imports, shared utilities, and implicit wiring~\cite{parnas1972informationhiding}. G1 treats boundary enforcement as a preventive control: making coupling explicit, reviewable, and auditable.

\subsection*{Applicability}
G1 applies to systems decomposed into bounded-context modules within a single codebase, where inter-module dependencies are explicitly declared and automatically verifiable. It assumes two-level decomposition: bounded contexts as first-class module boundaries, and package-by-feature organization within each module. G1 focuses on enforcing the \emph{outer} boundary; internal structuring rules are addressed in subsequent guidelines.

\subsection*{Objectives}

\emph{Research contributions:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Make modularity measurable and enforceable:} Define boundary enforcement as a measurable, automated constraint rather than an informal convention.
  \item \emph{Formalize the enforcement gap:} Demonstrate that conceptual knowledge of anti-patterns is insufficient without executable checks in the CI pipeline.
  \item \emph{Provide a composite boundary health gate:} Combine five boundary checks into a per-module binary gate ($b_m$) that feeds G2 maintainability and G3 extraction readiness.
\end{itemize}

\emph{Implementation objectives:}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Encapsulation and controlled dependency:} Keep internal classes hidden; allow cross-module access only through declared interfaces.
  \item \emph{Automated early verification:} Detect boundary violations at build or test time, not at runtime.
  \item \emph{Architectural drift prevention:} Defend module boundaries against convenience-driven erosion patterns.
\end{itemize}

\subsection*{Key Principles}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Explicit dependency declarations:} All dependencies on other modules must be declared in a central descriptor (annotation, configuration file, or build rule) so that boundary compliance is automatically verifiable. Component boundaries enforced at the programming model level make modularity a build-time property rather than a convention~\cite{ghemawat2023towards}.

  \item \emph{Contract-mediated communication:} Cross-module interaction occurs through public interfaces (synchronous calls) or domain events (asynchronous channels), never through direct references to another module's internals. This keeps each module's internal model free to evolve without coordinating with consumers~\cite{richardson2018microservices}.

  \item \emph{Boundary over feature convenience:} Package-by-feature improves cohesion within a bounded context, but a feature slice must not become a cross-module dependency path. When internal feature code is imported across boundaries, the module's encapsulation is violated regardless of how well-organized the internals are~\cite{parnas1972informationhiding}.
\end{itemize}

\subsection*{Implementation Mechanisms}
\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \emph{Structural encapsulation:} Separate public API packages from internal packages, and restrict visibility so that only the declared API is importable across module boundaries.
  \item \emph{Declarative dependency model:} Maintain a module descriptor that defines which modules are required and which are forbidden, and keep it version-controlled with boundary changes.
  \item \emph{Forbidden dependency declarations:} Declare module pairs that must never depend on each other to enforce stronger isolation where the domain requires it (for example, Payments must not import Shipments internals).
  \item \emph{Automated verification:} Fail the build when undeclared cross-module references are detected, and optionally verify event subscriptions and command usage against declared dependencies.
\end{itemize}

\subsection*{Common Failure Modes and Anti-Patterns}

\subsubsection*{Structural Anti-Patterns}

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \textbf{Convenience-Driven Imports} (Encapsulation Leakage rises)\\
  A developer imports an internal entity class directly from another module because the path is shorter than going through the public API. Over time, dozens of such shortcuts create a web of hidden coupling that locks the provider's internal structure in place~\cite{parnas1972informationhiding}.

  \item \textbf{Shared Utility Creep} (Undeclared Dependencies rise)\\
  A \texttt{shared/utils} package starts with generic helpers (date formatting, string validation) but gradually absorbs domain logic such as \texttt{calculateShippingCost} or \texttt{validatePaymentStatus}. Modules couple through this shared layer rather than through explicit contracts~\cite{martin2012clean}.

  \item \textbf{Implicit Wiring via Framework Magic} (Isolation Pass Rate drops)\\
  DI containers, auto-configuration, or classpath scanning silently wire modules together. A \texttt{@ComponentScan} annotation may inject a bean from one module into another without any declared dependency, creating coupling invisible to static analysis~\cite{rocha2021catalogingDI}.

  \item \textbf{Event Handlers Outside the Composition Root} (Event Violations rise)\\
  Event subscriptions are scattered across module initializers rather than centralized in a single wiring location. Each hidden subscription is a cross-module dependency that works at runtime but is invisible to architectural review~\cite{richardson2018microservices}.

  \item \textbf{Boundary Enforcement Treated as Optional}: all boundary metrics degrade\\
  When boundary verification is not a mandatory CI gate, violations accumulate silently across sprints. Teams discover the erosion only when an extraction attempt reveals that modules are far more coupled than the architecture documentation suggests~\cite{thoughtworks2017fitnessfunction}.
\end{itemize}

\subsubsection*{Design-Level Anti-Patterns}

\begin{itemize}[itemsep=8pt,topsep=2pt]
  \item \textbf{Extreme Granularity} (Undeclared Dependencies across many small modules)\\
  Teams slice the system into excessively narrow domains such as \texttt{StockCheck}, \texttt{ReservationHold}, \texttt{WarehouseAllocation}, and \texttt{StockReplenishment} instead of grouping them under a cohesive bounded context like \texttt{Inventory}. Each micro-domain cannot fulfill a business workflow independently, forcing constant cross-module calls for routine operations~\cite{dragoni2017microservices,evans2003ddd}.

  \item \textbf{Speculative Generality} (Encapsulation Leakage rises)\\
  The codebase accumulates abstract factories, strategy patterns, and extension hooks designed for hypothetical requirements that may never materialize. Each speculative abstraction adds exported types that cross module boundaries without serving a current need. The YAGNI principle~\cite{extremeProgramming} applies at the architectural level.

  \item \textbf{Leaky Abstractions in Public Contracts} (Encapsulation Leakage rises)\\
  A module exposes DTOs or event payloads that mirror its internal database schema (column names like \texttt{payment\_status\_id}, nullable fields reflecting storage trade-offs) rather than domain concepts. When the module refactors its schema, all consumers break even though no business rule changed~\cite{fowler2002,evans2003ddd}.

  \item \textbf{Circular Dependencies} (Forbidden Dependencies rise)\\
  Module A depends on B which depends on A, often through indirect paths spanning three or more modules. Cycles make independent testing and extraction impossible because changing any module in the cycle requires understanding all of them~\cite{martin2012clean,yourdon1979structured}. G1 treats any cycle as a blocking violation.

  \item \textbf{Test Coupling Across Boundaries} (Isolation Pass Rate drops)\\
  Test code in one module directly instantiates domain objects from another module to build fixtures or assert on internal state. A refactoring of the provider's entities breaks the consumer's test suite, even though production code respects the boundary~\cite{fairbanks2010justenough}.
\end{itemize}

\noindent
The SOLID principles, properly applied, address many of these failure modes: Single Responsibility prevents god modules, Open-Closed means extension through published contracts rather than speculative abstractions, and Dependency Inversion ensures modules depend on stable interfaces~\cite{martin2012clean}. In a modular monolith, SOLID serves boundary discipline, not architectural ornamentation.

\subsubsection*{The Enforcement Gap}

\noindent
Most of the failure modes described above are well known; experienced engineers recognize them on sight. Yet recognition alone does not prevent them, because these principles are rarely operationalized as measurable, automated constraints~\cite{fairbanks2010justenough}. They exist as shared understanding, not as executable checks in the CI pipeline.

This gap compounds with growth. A single convenience import is harmless; hundreds of locally reasonable shortcuts across months of fast-paced delivery produce systemic architectural drift that no amount of documentation or periodic review can reverse. By the time the drift becomes visible, typically during an extraction attempt, the cost of correction dwarfs the cost of prevention. The metrics and enforcement gates introduced in this guideline (and extended throughout G2 through G6) close this gap by translating what engineers already know into what the build system can verify on every commit.

\subsection*{Metrics and Verification}

All five boundary metrics act as binary gates: each must meet its target for the module to pass G1.

\subsection*{Core Contribution}

The contribution is not the individual practices (encapsulation, dependency declaration, automated testing are well-established) but a unified enforcement model that makes boundary discipline measurable and composable:

\begin{enumerate}[itemsep=8pt,topsep=2pt]
  \item \emph{The Enforcement Gap.} G1 formalizes the gap described above as a measurable architectural concern, not an informal observation.

  \item \emph{Five-metric boundary model.} Undeclared dependencies, forbidden references, encapsulation leakage, isolation pass rate, and event subscription violations provide complete coverage of structural, runtime, and data-flow coupling.

  \item \emph{Composite boundary health gate ($b_m$).} A per-module binary gate that feeds directly into G2 and G3, creating a composable chain across guidelines.
\end{enumerate}

\subsection*{Literature Support Commentary}

The principle that modules should encapsulate implementation details behind stable interfaces is well established~\cite{parnas1972informationhiding}, and boundary identification techniques are mature: a systematic review of 63 decomposition studies covers static analysis, dynamic analysis, and domain-driven approaches~\cite{abgaz2023decomposition}. However, the same review reveals that most approaches stop at \emph{identification}, proposing how to find boundaries but not how to enforce them once found. In practice, correct boundaries erode over time when no automated mechanism prevents violations~\cite{wolfart2021modernizing, deLauretis2019from}. In a microservices architecture, the network boundary enforces separation by default: a broken contract produces a runtime failure. In a monolith, a broken boundary produces a successful compilation, and the violation becomes visible only when extraction pressure arrives.

Two lines of recent work converge on G1's approach. First, the \textit{sliceable monolith} concept demonstrates that clean boundaries enable progressive decomposition without rewrites~\cite{montesi2021sliceable}, and component boundaries enforced at the programming model level make modularity a build-time property rather than a convention~\cite{ghemawat2023towards}. Second, industry experience validates that the modular monolith is a deliberate architectural choice rather than a transitional compromise~\cite{su2024modular, gravanis2021dont}, with boundary definition identified as a top decision driver for modulith adoption~\cite{prakash2024systematic} and automated enforcement as the decisive factor in controlling complexity at scale~\cite{shopify2020monolith, jovanovic2024rewriting}.

G1 addresses the gap between boundary identification and boundary enforcement. Where existing decomposition research tells teams \emph{where} to draw boundaries, G1 prescribes \emph{how} to make those boundaries automatically verifiable, ensuring that the architectural intent survives the pressure of daily development.

\section{G1 Applied: The Modular Tiny Store Example}
\label{sec:g1-demo-tiny-store}

The following sections operationalize G1 using Tiny Store, a small modular monolith maintained as an executable reference for this dissertation.\footnote{Full source: \url{https://github.com/maurcarvalho/tiny-store}} Two complementary feedback loops are used throughout: \texttt{npm run test:boundary} (structural rules) and \texttt{npm run test:integration} (cross-module behavior). The tutorial takes approximately 20--30 minutes.

\subsection*{Repository Orientation}

Tiny Store is a monorepo modular monolith organized around two top-level directories: \texttt{apps/} for deployable applications and \texttt{libs/} for reusable libraries. Four bounded-context modules (\texttt{orders}, \texttt{inventory}, \texttt{payments}, \texttt{shipments}) live under \texttt{libs/modules/}, each structured around \texttt{domain/} (aggregates, events, repositories), \texttt{features/} (use cases), and \texttt{listeners/} (event reactions).

Each module exposes a public entrypoint (\texttt{src/index.ts}) that re-exports only its public API; anything not exported is internal and invisible to other modules. The composition root (\texttt{register-listeners.ts}) centralizes all cross-module event subscriptions, making every integration point auditable in a single file. Shared code under \texttt{libs/shared/} is constrained to domain-neutral primitives (\texttt{shared-domain}) and infrastructure utilities (\texttt{shared-infrastructure}), ensuring that cross-cutting concerns do not introduce hidden coupling between bounded contexts. No module depends on another module directly; all inter-module collaboration flows through domain events wired in the composition root. Figure~\ref{fig:repo-orientation-diagram} shows the full repository structure.

  \caption{Repository-level orientation of the Tiny Store monorepo.}

\noindent
Cross-module collaboration follows event-driven choreography: modules communicate exclusively through domain events, with no direct cross-module imports. Each module reacts to events it subscribes to in the composition root, and the full lifecycle is traceable through the event chain (Figure~\ref{fig:order-events-lifecycle}).

This enforces a publish-subscribe contract: the producing module defines the event schema without knowledge of consumers, and each consumer translates the payload into its own domain operations. When Orders publishes \texttt{OrderPlaced}, Inventory reserves stock; once confirmed, Payments initiates a charge; and only after payment succeeds does Shipments prepare delivery. Each module reacts to the event relevant to its stage, and new consumers can be added without modifying the producer.

\subsection*{Tutorial: Step-by-Step Application}

Each step introduces a specific boundary enforcement mechanism, building incrementally from a clean baseline to a fully verified modular structure. The steps are reproducible on any monorepo with bounded-context modules managed by a workspace-aware build system such as Nx~\cite{nx2024}.

\begin{itemize}[itemsep=8pt,topsep=4pt]

  \item \emph{Step 0: Establish a Clean Baseline.}
  Run the three verification gates below. All must pass with zero violations: unit tests confirm module behavior, boundary tests verify that no undeclared or forbidden imports exist, and integration tests confirm that modules load correctly with only their declared dependencies.

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=bash,caption={Baseline checks for G1},label={lst:g1-baseline}]
npm install && npm test
npm run test:boundary
npm run test:integration
  \end{lstlisting}

  \item \emph{Step 1: Separate Public Surface from Internal Components.}
  Cross-module usage occurs only through module entrypoints (\texttt{@tiny-store/modules-*}):

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Public vs.\ internal imports},label={lst:g1-imports}]
// DO: import via public entrypoint (handler, not entity)
import { PlaceOrderHandler } from '@tiny-store/modules-orders';
// DON'T: entities and repositories are internal to the module
import { Order } from '@tiny-store/modules-orders';             // blocked
import { OrderRepository } from '@tiny-store/modules-orders';   // blocked
  \end{lstlisting}

  \item \emph{Step 2: Encode Explicit Declarations.}
  Express \emph{requires} and \emph{forbids} in a single, executable source of truth. The \texttt{requires} list declares allowed dependencies; the \texttt{forbids} list encodes domain invariants that must never be violated, making the decision to remove a prohibition explicit and reviewable rather than a silent one-line change:

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Code-based boundary descriptor},label={lst:g1-descriptor}]
export const moduleBoundaries = {
  orders:    { requires: ['shared-domain', 'shared-infrastructure'],
               forbids:  ['inventory', 'payments', 'shipments'] },
  inventory: { requires: ['shared-domain', 'shared-infrastructure'],
               forbids:  ['orders', 'payments', 'shipments'] },
} as const;
  \end{lstlisting}

  \item \emph{Step 3: Centralize Cross-Module Wiring.}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Composition root wiring (\texttt{register-listeners.ts})},label={lst:g1-do-wiring}]
// DO: centralized in the composition root (auditable)
import { OrderPlacedListener } from '@tiny-store/modules-inventory';
eventBus.subscribe('OrderPlaced', (e) => new OrderPlacedListener().handle(e));
\end{lstlisting}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Hidden wiring inside a module (avoid)},label={lst:g1-dont-hidden-wiring}]
// DON'T: wiring inside a module makes dependencies implicit
EventBus.getInstance().subscribe('OrderPlaced', handler);
\end{lstlisting}

  \item \emph{Step 4: Enforce Boundary Verification as a First-Class Gate.}
  The gate is binary: pass (no violations) or fail with exact dependency location.

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=bash,caption={Boundary verification gate},label={lst:g1-boundary-gate}]
npm run test:boundary

# Boundary violation detected
# Source:    libs/modules/orders
# Forbidden: libs/modules/inventory/src/domain/Product.ts
# Fix: use public handler, event+listener, or promote to libs/shared/
\end{lstlisting}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Public surface test},label={lst:g1-boundary-spec}]
describe('Module Public Surface', () => {
  it('does not expose Inventory internals', async () => {
    const mod = await import('@tiny-store/modules-inventory');
    expect((mod as any).Product).toBeUndefined();
    expect((mod as any).InventoryRepository).toBeUndefined();
  });
  it('exposes Orders public handlers', async () => {
    const mod = await import('@tiny-store/modules-orders');
    expect((mod as any).PlaceOrderHandler).toBeDefined();
  });
});
\end{lstlisting}

  \item \emph{Step 5: Add Module Isolation Checks.}
  Detect runtime coupling invisible to static analysis:

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Module isolation test},label={lst:g1-isolation}]
it('loads orders with declared dependencies only', async () => {
  const mod = await loadModule('orders',
    { allowed: ['shared-domain', 'shared-infrastructure'] });
  expect(mod).toBeDefined();
});
  \end{lstlisting}

\end{itemize}

\subsection*{Exercise Walkthrough: Controlled Violations and Signals}
Each exercise introduces a single, controlled boundary breach and observes the failure signal. All exercises pass G1's boundary gate at baseline; the violation produces a specific, measurable signal.

\subsubsection*{Exercise Summary}
Each exercise assumes a clean baseline (Step 0 passes). After each exercise, revert the violation before proceeding to the next.
\begin{itemize}[itemsep=2pt,topsep=2pt]
  \item \textbf{Ex.\,1:} Export internal types → Encapsulation Leakage rises.
  \item \textbf{Ex.\,2:} Direct cross-module import → Undeclared/Forbidden Dependencies rise.
  \item \textbf{Ex.\,3:} Subscribe inside module → Isolation Pass Rate drops.
\end{itemize}

\subsubsection*{Exercises}
\begin{itemize}[itemsep=10pt,topsep=4pt]

  \item \emph{Exercise 1: Encapsulation Leak (export internal types).}
  In \texttt{libs/modules/orders/src/index.ts}:

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Violation: exporting internal types},label={lst:g1-ex1-leak}]
// VIOLATION: exporting internal domain types leaks encapsulation
export * from './domain/entities/order';
export * from './domain/repositories/order-repository';
  \end{lstlisting}

  \noindent
  Run \texttt{npm run test:boundary}: fails because Encapsulation Leakage rises.\\
  \emph{Resolution:} remove these exports; expose a contract instead (handler/port/event).

  \item \emph{Exercise 2: Direct Cross-Module Import (undeclared dependency).}
  In an Orders feature file:

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Violation: direct cross-module import},label={lst:g1-ex2-import}]
// VIOLATION: Orders directly imports Inventory
import { SomeInventoryHandler } from '@tiny-store/modules-inventory';
  \end{lstlisting}

  \noindent
  Run \texttt{npm run test:boundary}: fails because Undeclared or Forbidden Dependencies rise.\\
  \emph{Resolution:} replace with event-driven collaboration (publish \texttt{OrderPlaced}, react in Inventory).

  \item \emph{Exercise 3: Hidden Event Wiring (implicit dependency).}
  Inside a module's \texttt{listeners/} file:

  \begin{lstlisting}[basicstyle=\ttfamily\scriptsize,language=TypeScript,caption={Violation: hidden event wiring},label={lst:g1-ex3-hidden-wiring}]
// VIOLATION: hidden event wiring inside a module
EventBus.getInstance().subscribe('OrderPlaced', (e) => this.handle(e));
  \end{lstlisting}

  \noindent
  Run \texttt{npm run test:boundary \&\& npm run test:integration}: Isolation Pass Rate drops.\\
  \emph{Resolution:} move the subscription to \texttt{register-listeners.ts}.
\end{itemize}

\subsection*{Conclusion}

The exercises revealed an important asymmetry: every violation that G1 catches is architecturally harmful, but not every architecturally harmful change triggers a G1 violation. A module can pass all five boundary checks while quietly accumulating the kind of coupling that makes future changes expensive: a growing public surface that every consumer must track, a concentration of inbound dependencies on a single module, or a contract that changes with every release. These are not boundary problems; they are \emph{evolution} problems, and they require a different class of metric.

This asymmetry is what connects the Architectural Design guidelines into a progression rather than a checklist. G1's binary gate ($b_m$) answers a structural question: \emph{can} modules operate independently? But a passing gate says nothing about \emph{whether} that independence is being preserved as the codebase evolves. G2 picks up exactly where this blind spot begins, shifting from static boundary verification to tracking how module interfaces change over time: coupling direction, surface stability, and the rate at which cross-module dependencies accumulate. G3 then extends the same logic to infrastructure: even with clean boundaries and stable interfaces, a module that shares its database schema or communicates exclusively through synchronous calls cannot be extracted without rewriting its data access layer.

Each guideline, in other words, protects against a category of degradation that the previous one is structurally unable to detect. The result is a layered verification model where $b_m$ feeds into G2's maintainability assessment, which in turn feeds into G3's extraction readiness score ($\varepsilon_m$). A team that enforces only G1 will have clean boundaries that silently calcify; a team that enforces G1 and G2 will have maintainable modules that cannot be extracted; only the complete chain produces a system where extraction, when warranted, is a configuration change rather than a rewrite.
