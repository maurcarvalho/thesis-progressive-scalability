\section{Foundations for the Architectural Design Dimension}
\label{sec:background-architectural-design}

A modular monolith structures the application as a single deployable unit whose internals consist of well-defined, self-contained modules. By imposing strict boundaries and interfaces, this approach preserves benefits commonly associated with distributed architectures (parallel development, maintainability, scalability) while avoiding a substantial portion of the operational complexity of distributed systems~\cite{abgaz2023decomposition, grzybek2020modular}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.90\linewidth]{Cap4/guidelines/modular-deployment-units.png}
  \caption[Deployment units in modular monoliths and microservices]{Deployment units in modular monoliths and microservices. The left side illustrates a modular monolith, where domain-aligned modules execute within a single runtime and may share a single data store, while enforcing internal boundaries through code-level constraints. The right side illustrates microservices, where each service runs as an independent runtime and typically owns its persistence, enabling independent deployment and scaling at the cost of distributed-system operational overhead. Source: Dr Milan Milanović (adapted for this research).}
  \label{fig:modular-deployment-units}
\end{figure}

Progressive scalability depends first on enforceable modularity: clear boundaries, explicit contracts, and build-time checks that detect boundary corruption early. The guidelines are presented by impact, with G1 as the foundation: without verifiable boundary enforcement, later guidelines cannot assume stable module interfaces.

Architectural design can be framed as an evolutionary progression in separation of concerns, from technical separation (MVC, layered structures) toward dependency discipline and domain-centric organization~\cite{cockburn2005hexagonal,palermo2008onion,martin2012clean}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.75\linewidth]{Cap4/guidelines/domain-centric-layered-arch.png}
  \caption[Layered architecture versus domain-centric architecture]{Layered versus domain-centric architecture. Domain-centric design shifts the primary decomposition axis from technical layers to business capabilities, improving cohesion and reducing cross-cutting coupling.}
  \label{fig:layered-vs-domain-architecture}
\end{figure}

In parallel, packaging strategies evolved from technical layers to feature slices, and then to component-like modules aligned with domain boundaries~\cite{shaw2018vertical}.

\subsection*{Cost of Change: Coupling and Cohesion}

Cost of change is often dominated by dependency structure rather than by local code complexity. Interactions are where change propagates, coordination increases, and unintended side effects emerge. Structured design theory provides a rigorous vocabulary for this relationship~\cite{yourdon1979structured}. Three claims are central to G1--G3:

\begin{itemize}
    \item \textbf{Not all coupling is equal.} Some dependencies are stabilizing and intentional (inside a coherent boundary); others are accidental and create ripple effects across unrelated areas.
    \item \textbf{Decoupling has its cost.} Indirection and additional interfaces reduce harmful dependency but may increase cognitive load if applied without need.
    \item \textbf{Cohesion is coupling in the right places.} Coupling is not eliminated but relocated into cohesive units so that change remains localized.
\end{itemize}

Software design can therefore be treated as the act of modeling units of \textbf{strong cohesion, loosely coupled} to each other. G1--G3 operationalizes this by making coupling explicit, constraining it through boundary rules, and aligning modules with business capabilities. Functional decomposition is preferred over technical decomposition when the goal is to reduce change amplification, because it localizes business evolution inside bounded units. A recurring risk is mistaking organization for encapsulation: directory structure alone does not enforce boundaries unless backed by interface contracts and dependency rules.

\subsection*{Modular Decomposition Styles: Horizontal vs Vertical}
In traditional layered architectures, code is structured by technical responsibility (presentation, services, persistence). While this provides separation of concerns, it disperses domain logic across layers: modifications to a single feature require coordinated changes across all layers~\cite{fowler2002patterns}.

Figure~\ref{fig:change-coupling-ripple} illustrates this propagation: a change at the origin node ripples through the dependency graph, impacting structurally coupled but functionally unrelated components.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.40\linewidth]{Cap4/guidelines/change-coupled-effect.png}
  \caption[Coupled-change ripple in a dependency graph]{Coupled-change ripple in a dependency graph. Nodes represent components and directed edges represent dependencies. The change originates at the top node and propagates along dependency paths. Darker nodes indicate impacted components; concentric halos emphasize the spread of change through tighter coupling.}
  \label{fig:change-coupling-ripple}
\end{figure}

Vertical decomposition addresses this by organizing code around domain capabilities. All elements for a specific behavior (API endpoints, business logic, data access) are grouped within a single module~\cite{shaw2018vertical}, increasing cohesion and reducing cross-feature coupling.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.6\linewidth]{Cap4/guidelines/layered-vs-modular.png}
  \caption[Layered and modular architecture]{Layered and modular architecture. The left side shows a traditional layered decomposition by technical responsibility. The right side shows a modular decomposition where domain modules each contain their own UI/API, application logic, and persistence, keeping feature changes localized within module boundaries.}
  \label{fig:layered-vs-modular}
\end{figure}

A key risk is architectural \textit{cargo culting}: adopting a packaging style without understanding the coupling problem it solves, particularly when architecture is documented as diagrams but not enforced in code.

\subsection*{Screaming Architecture: Domain Alignment and Model--Code Gap}

A \emph{screaming architecture} communicates its business purpose at a glance: the top-level organization foregrounds domain concepts rather than frameworks or technical layering~\cite{martin2012clean,martin2011screaming}. When technical concerns dominate the structure, engineers must reconstruct domain intent from dispersed artifacts, increasing cost of change.

This connects to the \emph{model--code gap}: the divergence between documented and implemented architecture~\cite{fairbanks2010justenough}. An \emph{architecturally-evident coding style} encodes decisions directly into module boundaries and enforced dependency rules, making boundaries explicit, inspectable, and continuously verified~\cite{fairbanks2010justenough}.

\subsection*{Separation of Concerns and Dependency Discipline}

Layered Architecture structures dependencies by technical responsibility (Presentation, Business, Persistence)~\cite{fowler2002patterns}. While layering improves local reasoning, it may amplify change cost when features cut across layers and domain logic fragments into anemic models.

Hexagonal, Onion, and Clean Architecture formalize a stricter rule: business logic is insulated from delivery and infrastructure, and dependencies point inward toward stable domain abstractions~\cite{cockburn2005hexagonal,palermo2008onion,martin2012clean}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.64\linewidth]{Cap4/guidelines/hexa-onion-modular.png}
  \caption[From layered to modular architecture styles]{Comparison of architectural decomposition styles.}
  \label{fig:layered-vs-hexagonal-vs-modular}
\end{figure}

Dependency inversion reduces coupling to volatile infrastructure: replacements, testing strategies, and delivery mechanisms can evolve without rewriting core domain logic. However, dependency discipline alone does not guarantee domain-centric modularity. A codebase can follow inward dependencies and still be a single, tightly coupled domain blob if boundaries between business capabilities are not explicit.

\subsection*{Packaging and Slicing Strategy}
Packaging strategy determines what coupling is easy and what is discouraged. G1--G3 depends on understanding what each strategy optimizes for and where it fails.

\emph{Package by layer} organizes code by technical responsibility (controllers, services, repositories). Business changes span multiple packages, amplifying cost of change. Delivery pressure reinforces this: short-term convenience encourages cross-layer shortcuts until the system reflects technical decomposition rather than business capability.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.75\linewidth]{Cap4/guidelines/package-by-layer-dir.png}
\end{figure}

\emph{Package by feature} organizes code around domain capabilities, localizing behavior rather than scattering it across layers~\cite{shaw2018vertical}. The failure mode is features becoming folders without stable interfaces, reintroducing hidden coupling through shared utilities and unrestricted imports.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.75\linewidth]{Cap4/guidelines/package-by-feature-dir.png}
\end{figure}

\emph{Package by component} organizes code around cohesive components accessed through well-defined interfaces~\cite{evans2003ddd}. Component boundaries become enforceable when they define what is exposed publicly, what is hidden internally, and which dependency directions are permitted. This is the closest analogue to modules in a modular monolith. The failure mode arises when components are not aligned with bounded contexts: overly coarse components accumulate unrelated responsibilities, while overly fine-grained components fragment aggregates.

\subsection*{Modularity as an Enforceable Principle}

This research treats modularity as an enforceable property, not a folder convention. Encapsulation and information hiding minimize potential dependencies by reducing what other modules can see and use~\cite{parnas1972criteria}. This implies several principles that G1--G3 operationalizes:

\begin{itemize}
    \item Separating interface from implementation: modules expose a small public API and keep internals private.
    \item Minimizing cross-module imports to reduce change propagation paths.
    \item Matching public surface area to architectural intent, so that exports reflect intended coupling.
    \item Splitting the source tree into explicit module roots for architectural visibility and boundary enforcement.
\end{itemize}

\textbf{Encapsulation over organization}: directory structure matters only when backed by dependency rules, stable interfaces, and verification mechanisms. Without enforcement, modularity claims collapse under delivery pressure.

Tiny Store~\cite{tinystore2026} serves as the reference implementation, providing an auditable codebase where packaging strategies and boundary enforcement can be inspected directly.

\subsection*{Definition of Module Quality}

G1--G3 treats module quality as a measurable architectural objective. Modules are expected to satisfy:

\begin{itemize}
    \item High cohesion and low coupling
    \item Focus on a specific, self-contained business capability
    \item Alignment to a bounded context or aggregate
    \item Encapsulated data ownership
    \item Substitutability and composability with other modules
\end{itemize}

This checklist serves as the baseline for designing boundaries, defining public APIs, and evaluating whether a proposed decomposition reduces change cost rather than reshuffles code.

\subsection*{From Foundations to Guidelines}

The causal chain is: coupling patterns dominate change cost, cohesion localizes change, separation of concerns reduces dependency on volatile infrastructure, and packaging strategy determines whether code structure reflects domain intent. Modularity becomes sustainable only when interfaces, dependency direction, and enforcement mechanisms make boundaries explicit and verifiable. G1--G3 translates these foundations into actionable specifications supported by the Tiny Store reference implementation.
