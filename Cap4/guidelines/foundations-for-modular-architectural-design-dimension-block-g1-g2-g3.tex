\section{Foundations for the Architectural Design Dimension}
\label{sec:background-architectural-design}

A modular monolith deploys as a single unit but enforces strict internal boundaries between self-contained modules, preserving key benefits of distributed architectures (parallel development, maintainability, scalability) without proportional operational complexity~\cite{abgaz2023decomposition, grzybek2020modular}.

Progressive scalability requires enforceable modularity. The guidelines are ordered by impact: G1 establishes boundary enforcement as the foundation, because later guidelines depend on stable module interfaces. Architecturally, this reflects a progression from technical separation (MVC, layered structures) toward dependency discipline and domain-centric organization~\cite{cockburn2005hexagonal,palermo2008onion,martin2012clean}.

  \label{fig:layered-vs-domain-architecture}
\end{figure}

In parallel, packaging strategies evolved from technical layers to feature slices, and then to component-like modules aligned with domain boundaries~\cite{shaw2018vertical}.

\subsection*{Cost of Change: Coupling and Cohesion}

Cost of change is dominated by dependency structure, not local code complexity~\cite{yourdon1979structured,khononov2024balancing}. Not all coupling is equal: intentional dependencies inside a coherent boundary are stabilizing, while accidental ones create ripple effects across unrelated areas~\cite{khononov2024balancing}. Decoupling itself has a cost, as indirection may increase cognitive load if applied without need. The goal is not to eliminate coupling but to relocate it into cohesive units so that change remains localized: \textbf{strong cohesion, loosely coupled}.

Functional decomposition is preferred over technical decomposition because it localizes business evolution inside bounded units. However, domain-aligned folders alone do not enforce boundaries unless backed by interface contracts and dependency rules. G1--G3 operationalizes this by making coupling explicit, constraining it through verifiable rules, and providing metrics that detect when organizational structure diverges from actual enforcement.

\subsection*{Modular Decomposition Styles: Horizontal vs Vertical}
In traditional layered architectures, code is structured by technical responsibility (presentation, services, persistence). While this provides separation of concerns, it disperses domain logic across layers: modifications to a single feature require coordinated changes across all layers~\cite{fowler2002patterns}.


\begin{figure}[H]
  \centering
  \includegraphics[width=0.40\linewidth]{Cap4/guidelines/change-coupled-effect.png}
  \caption[Coupled-change ripple in a dependency graph]{Coupled-change ripple in a dependency graph. A single change propagates along dependency edges; darker nodes indicate impacted components.}
  \label{fig:change-coupling-ripple}
\end{figure}

Vertical decomposition addresses this by organizing code around domain capabilities. All elements for a specific behavior (API endpoints, business logic, data access) are grouped within a single module~\cite{shaw2018vertical}, increasing cohesion and reducing cross-feature coupling.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.5\linewidth]{Cap4/guidelines/layered-vs-modular.png}
  \caption[Layered and modular architecture]{Layered (by technical responsibility) versus modular (by domain capability) decomposition. Modular decomposition localizes feature changes within module boundaries.}
  \label{fig:layered-vs-modular}
\end{figure}

A key risk is architectural \textit{cargo culting}: adopting a packaging style without understanding the coupling problem it solves, particularly when architecture is documented as diagrams but not enforced in code.

\subsection*{Screaming Architecture: Domain Alignment and Model--Code Gap}

A \emph{screaming architecture} communicates its business purpose at a glance: the top-level organization foregrounds domain concepts rather than frameworks or technical layering~\cite{martin2012clean,martin2011screaming}. When technical concerns dominate the structure, engineers must reconstruct domain intent from dispersed artifacts, increasing cost of change.

This connects to the \emph{model--code gap}: the divergence between documented and implemented architecture~\cite{fairbanks2010justenough}. An \emph{architecturally-evident coding style} encodes decisions directly into module boundaries and enforced dependency rules, making boundaries explicit, inspectable, and continuously verified~\cite{fairbanks2010justenough}.

\subsection*{Separation of Concerns and Dependency Discipline}

Layered Architecture structures dependencies by technical responsibility (Presentation, Business, Persistence)~\cite{fowler2002patterns}. While layering improves local reasoning, it may amplify change cost when features cut across layers and domain logic fragments into anemic models.

Hexagonal, Onion, and Clean Architecture formalize a stricter rule: business logic is insulated from delivery and infrastructure, and dependencies point inward toward stable domain abstractions~\cite{cockburn2005hexagonal,palermo2008onion,martin2012clean}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.64\linewidth]{Cap4/guidelines/hexa-onion-modular.png}
  \caption[From layered to modular architecture styles]{Comparison of architectural decomposition styles.}
  \label{fig:layered-vs-hexagonal-vs-modular}
\end{figure}

Dependency inversion reduces coupling to volatile infrastructure: replacements, testing strategies, and delivery mechanisms can evolve without rewriting core domain logic. However, dependency discipline alone does not guarantee domain-centric modularity. A codebase can follow inward dependencies and still be a single, tightly coupled domain blob if boundaries between business capabilities are not explicit.

\subsection*{Packaging Strategy}

Packaging strategy determines the default coupling direction in a codebase: it makes certain dependencies convenient and others costly. Three strategies represent a progression toward domain-centric modularity, each addressing a limitation of the previous one.

\emph{Package by layer} groups code by technical responsibility: controllers, services, and repositories each occupy a separate package~\cite{fowler2002patterns}. This provides separation of concerns at the infrastructure level but disperses domain logic across layers. A single business change (e.g., adding a field to an order) requires coordinated modifications in the presentation, service, and persistence layers. Under delivery pressure, cross-layer shortcuts accumulate until the system's structure reflects its technology stack rather than its business capabilities.

\emph{Package by feature} addresses this dispersion by grouping all elements of a business capability (API, logic, persistence) into a single package~\cite{shaw2018vertical}. This increases cohesion and reduces cross-feature coupling. However, without enforced interfaces, features become folders rather than boundaries: shared utilities and unrestricted imports reintroduce the coupling that the reorganization was meant to eliminate.

\emph{Package by component} adds the enforcement layer that package by feature lacks. Components expose a public interface and hide internal implementation, with explicit rules governing which dependencies are permitted~\cite{evans2003ddd}. This is the closest packaging analogue to modules in a modular monolith. The strategy fails when component granularity does not match bounded contexts: overly coarse components accumulate unrelated responsibilities, while overly fine-grained components fragment aggregates and force excessive cross-component communication.

The progression from layer to feature to component mirrors the architectural evolution described earlier: from technical separation to domain alignment to enforceable boundaries. G1--G3 assumes package-by-component as the baseline and provides the metrics to verify that component boundaries remain effective under sustained development.

\subsection*{Modularity as an Enforceable Principle}

This research treats modularity as an enforceable property, not a folder convention. Encapsulation and information hiding minimize potential dependencies by reducing what other modules can see and use~\cite{parnas1972informationhiding}. This implies several principles that G1--G3 operationalizes:

\begin{itemize}
    \item Separating interface from implementation: modules expose a small public API and keep internals private.
    \item Minimizing cross-module imports to reduce change propagation paths.
    \item Matching public surface area to architectural intent, so that exports reflect intended coupling.
    \item Splitting the source tree into explicit module roots for architectural visibility and boundary enforcement.
\end{itemize}

\textbf{Encapsulation over organization}: directory structure matters only when backed by dependency rules, stable interfaces, and verification mechanisms. Without enforcement, modularity claims collapse under delivery pressure.

Tiny Store\footnote{\url{https://github.com/maurcarvalho/tiny-store}} serves as the reference implementation, providing an auditable codebase where packaging strategies and boundary enforcement can be inspected directly.

\subsection*{Definition of Module Quality}

G1--G3 treats module quality as a measurable architectural objective. Modules are expected to satisfy:

\begin{itemize}
    \item High cohesion and low coupling
    \item Focus on a specific, self-contained business capability
    \item Alignment to a bounded context or aggregate
    \item Encapsulated data ownership
    \item Substitutability and composability with other modules
\end{itemize}

This checklist serves as the baseline for designing boundaries, defining public APIs, and evaluating whether a proposed decomposition reduces change cost rather than reshuffles code.

\subsection*{From Foundations to Guidelines}

The causal chain is: coupling patterns dominate change cost, cohesion localizes change, separation of concerns reduces dependency on volatile infrastructure, and packaging strategy determines whether code structure reflects domain intent. Modularity becomes sustainable only when interfaces, dependency direction, and enforcement mechanisms make boundaries explicit and verifiable. G1--G3 translates these foundations into actionable specifications supported by the Tiny Store reference implementation.
